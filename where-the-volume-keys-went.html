Where the Volume Keys Went

On Linux, the Surface Laptop SE's volume and brightness keys have done nothing since at least 2022. This is how we followed a single keypress through the keyboard controller, the firmware and two kernel drivers, and found where it was being thrown away.

The short version

Those keys never reach the keyboard. The embedded controller (EC) turns them into ACPI notifications for a firmware device called BIND, hardware ID MSHW0040. Linux has two drivers that know that ID, and both reject this laptop's version of it. With nothing bound to the device, every volume, brightness and power keypress is silently dropped.

The fix is a small kernel driver that binds MSHW0040 on this one model and turns the notifications back into key presses. It can be installed today with DKMS, and there's a matching patch for the upstream kernel.

01This isn't the hardware we expected

The obvious suspects were the linux-surface drivers: surface_aggregator, surface_hid_core and surface_kbd. Most modern Surfaces route their keyboard through the Surface Aggregator Module (SAM). The first look at the input devices showed that the Laptop SE doesn't:

N: Name="AT Translated Set 2 keyboard"
P: Phys=isa0060/serio0/input0      # plain PS/2, via the i8042 controller

surface_gpe: no compatible Microsoft Surface device found, exiting

The Laptop SE is a budget Gemini Lake machine. Its keyboard is ordinary PS/2, and there's no SAM at all. The drivers named in the bug report never touch it, so the problem had to be somewhere else.

02Listening to the keys

With the keyboard controller's debug logging on (/sys/module/i8042/parameters/debug), we recorded every input device with evtest, plus acpi_listen and the kernel log, and pressed each key in turn.

KeyWhat the kernel saw
Mutescancode e0 20 → KEY_MUTE (already worked)
Play/Pausescancode e0 22 → KEY_PLAYPAUSE
Fn + those keysplain F2, F3, F4, F6, F7
Volume ±, Brightness ±nothing at all: no event and no i8042 interrupt

That last row rules out the usual fix. Normally an unknown key logs atkbd: Unknown key pressed, and a one-line udev hwdb rule maps it to the right key code. Here the keyboard controller never hears the keypress, so there's nothing to remap. The key has to be reaching the system some other way.

03Reading the firmware

The other way in is ACPI, the firmware's description of the hardware. We dumped the tables with acpidump and decompiled them with iasl -d. In the embedded controller's section of the DSDT is a row of EC query methods: small routines the EC triggers by number.

Method (_QD1, 0, NotSerialized)
{
    P80H = 0xD1
    Notify (BIND, 0xC0)   // Hardware-Specific
}
…  _QD1–_QD6 → BIND 0xC0–0xC3, 0xC6, 0xC7
   _Q16/_Q17 → BIND 0xCA/0xCB   _Q1B/_Q1C → BIND 0xCC/0xCD

0xC0–0xC7 is the event-code scheme Microsoft used for the Surface Pro 4's hardware buttons. The device receiving them looked familiar:

Device (BIND)
{
    Name (_HID, "MSHW0040")
    Method (_DSM, 4, Serialized)   // UUID 6fd05c69-cde3-49f4-95ed-ab1665498035
    {  …  Case (0x02) { Return (0x4E) }  …  }   // "OEM platform revision"
}

Linux knows MSHW0040. Yet /sys/bus/acpi/devices/MSHW0040:00 showed no driver bound, even though both drivers that claim that ID were loaded.

04Why nobody was listening

Microsoft reused MSHW0040 across generations with two different designs. On the Pro 4 and Book 1, buttons arrive as notifications like these. On the Pro 5 and later, they're wired to GPIO pins. The kernel tells the two apart with the _DSM "OEM platform revision": 0 means the notification design, anything else means GPIO. The Laptop SE breaks that rule: it uses notifications but reports revision 0x4E.

DriverWhat it requiresLaptop SEResult
surfacepro3_buttonobject named VGBI, and OEM revision = 0named BIND, revision 0x4Erejects
soc_button_arrayOEM revision ≠ 0, and GPIO resourcesrevision passes, but no _CRS/GPIOsrejects

Each driver correctly decides the device isn't one of its own, so it ends up with neither. ACPI notifications for a device with no driver are dropped without a log message, which is why nothing ever showed up in acpi_listen. The power button turned out to be affected too:

ACPI Error: No installed handler for fixed event - PowerButton (2), disabling

05Proving which key fires which event

The DSDT showed which notifications exist, but not which key sends which. To find out, we turned on the kernel's embedded-controller debug messages. These log every query the EC raises:

echo 'file drivers/acpi/ec.c +p' | sudo tee /proc/dynamic_debug/control

Then we pressed each key a different number of times: Brightness Down once, Brightness Up twice, Volume Down three times, Volume Up four times. Each query number in the log appeared exactly as many times as its key was pressed, so the mapping reads straight off the counts.

[5809.00] ACPI: EC: Query(0x1b) started   ← Brightness Down ×1
[5809.16] ACPI: EC: Query(0x1c) started     (release)
[5812.62] ACPI: EC: Query(0x16) started   ← Brightness Up ×2
…
[5821.43] ACPI: EC: Query(0xd1) started   ← Volume Up ×4
KeyEC queriesNotify code (press / release)
Volume Up_QD1 / _QD20xC0 / 0xC1
Volume Down_QD3 / _QD40xC2 / 0xC3
Power_QD5 / _QD60xC6 / 0xC7
Brightness Up_Q16 / _Q170xCA / 0xCB (new)
Brightness Down_Q1B / _Q1C0xCC / 0xCD (new)

The volume and power codes are the same ones surfacepro3_button already handles for the Pro 4. The two brightness pairs are new, and no existing driver knows them.

06The fix

The fix is a small platform driver (under 200 lines), surface_laptop_se_buttons. It binds MSHW0040 only when DMI identifies the machine as a Surface Laptop SE, installs an ACPI notify handler, and translates the codes into standard key events. The core of it:

static void slse_notify(acpi_handle handle, u32 event, void *data)
{
	…
	bool pressed = !(event & 1);	/* even = press, odd = release */

	switch (event) {
	case 0xc0: case 0xc1: key_code = KEY_VOLUMEUP;       break;
	case 0xc2: case 0xc3: key_code = KEY_VOLUMEDOWN;     break;
	case 0xc6: case 0xc7: key_code = KEY_POWER;          break;
	case 0xca: case 0xcb: key_code = KEY_BRIGHTNESSUP;   break;
	case 0xcc: case 0xcd: key_code = KEY_BRIGHTNESSDOWN; break;
	…

Loaded with insmod, it bound immediately (surface_laptop_se_buttons MSHW0040:00: Surface Laptop SE buttons [BIND]). evtest showed a clean press and release for every key, and the desktop's volume and brightness indicators appeared. The full source is further down.

07Two loose ends

The Search key

Search already worked at the kernel level. It sends scancode e0 65, which Linux reports as KEY_SEARCH. The desktop just had nothing bound to it. On COSMIC, a custom shortcut fixes it: XF86Search → Launcher. On GNOME, KDE and others, bind it in the keyboard shortcut settings.

Holding a key doesn't repeat

Holding Volume Up raised the volume by one step and stopped. The first guess was that the driver needed kernel key repeat (EV_REP). The kernel did start repeating, about every 34 ms, with 160 repeat events during one hold, but nothing changed on screen. The EC trace showed it reports a real hold (press, then release 2.5 s later), so the problem wasn't the hardware either. On Wayland the compositor decides whether a held key repeats, and libinput deliberately discards the kernel's repeat events. COSMIC doesn't repeat volume or brightness shortcuts on any keyboard; this is an open issue, cosmic-epoch#384. The lesson: measure every layer before you blame one. The upstream patch was kept simple as a result.

08Installing it

The driver has no distro-specific code. What matters is the kernel version and whether Secure Boot is on.

  • Kernel 6.11 or newer: works as-is. It was built and tested on 7.1.5.
  • Kernel 6.7–6.10: covered by a compatibility fallback in the source, but not yet tested on those kernels.
  • Older than 6.7: not supported.
sudo mkdir -p /usr/src/surface_laptop_se_buttons-0.3
# copy surface_laptop_se_buttons.c, Makefile and dkms.conf (below) into that directory
sudo dkms install -m surface_laptop_se_buttons -v 0.3
sudo modprobe surface_laptop_se_buttons

DKMS rebuilds the module automatically on every kernel update, and it loads at boot because it matches the ACPI device ID.

Pop!_OS, Ubuntu, Mint

sudo apt install dkms linux-headers-$(uname -r). Mint 22.2 and 22.3 ship kernel 6.14, which works as-is.

LMDE 7, Debian 13

sudo apt install dkms linux-headers-$(uname -r). LMDE 7 ships kernel 6.12, which works as-is. LMDE 6 and Debian 12 (kernel 6.1) are too old unless you install a newer kernel from backports.

Fedora

sudo dnf install dkms kernel-devel

Arch

sudo pacman -S dkms linux-headers. The linux-surface kernel works too; its MSHW0040 drivers reject this device in the same way.

With Secure Boot on

Secure Boot only loads kernel modules signed by a key the firmware trusts. You need to enrol a Machine Owner Key (MOK) once, and after that DKMS signs every rebuild automatically. The only difference between distro families is where DKMS keeps the key:

Distro familyPublic key to enrolPrompts you during install?
Ubuntu, Pop!_OS, Mint/var/lib/shim-signed/mok/MOK.derusually
Debian, LMDE/var/lib/dkms/mok.pubno, so always do step 2
  1. Install the module as above. DKMS creates a signing key and signs the module with it. On Ubuntu-based systems, if the installer prompts you for a password, choose one and skip step 2.
  2. Otherwise, request enrollment yourself: sudo mokutil --import <key from the table> (for example /var/lib/dkms/mok.pub on LMDE), and choose a one-time password.
  3. Reboot. A blue MOK Manager screen appears before Linux starts. Choose Enroll MOK → Continue → Yes and enter that password.
  4. Check it with mokutil --list-enrolled, then sudo modprobe surface_laptop_se_buttons.

You do this once. Kernel updates are signed with the same key. Immutable distros (Silverblue, Bazzite, SteamOS) make adding kernel modules hard; they'll have to wait for the upstream fix.

09Getting it upstream

Once a fix is in the mainline kernel, every distro gets it automatically, with no DKMS and no signing. A patch has been prepared that teaches the existing surfacepro3_button driver about the Laptop SE: it recognises the BIND object on this model by DMI, skips the VGBI/revision checks for it, and adds the brightness codes. It compiles against 7.1 and passes checkpatch.pl with 0 errors and 0 warnings. It hasn't been sent to the maintainers or the platform-driver-x86 list yet.

10The toolbox

None of this is specific to Surface hardware. If a hotkey on any laptop does nothing, these checks find out where it disappears.

QuestionTool
Does the key produce an input event?sudo evtest
Does the keyboard controller see anything?echo 1 > /sys/module/i8042/parameters/debug, then read dmesg
Is it an unmapped scancode?look for atkbd: Unknown key pressed in dmesg (fixed with a udev hwdb rule)
Does it raise an EC query?echo 'file drivers/acpi/ec.c +p' > /proc/dynamic_debug/control
What does the firmware do with it?acpidump, acpixtract -a, iasl -d, then grep for _Qxx and Notify
Is a driver bound to that device?readlink /sys/bus/acpi/devices/<ID>/physical_node/driver
Why did the driver reject it?read the driver's probe() function in the kernel source
A privacy note. i8042.unmask_kbd_data writes every raw keystroke to the kernel log, and that includes passwords. Turn it on for a few seconds at most, press only the key you're testing, and turn it off again.

The driver source

surface_laptop_se_buttons.c 
// SPDX-License-Identifier: GPL-2.0-only
/*
 * Hotkey support for the Microsoft Surface Laptop SE.
 *
 * The EC reports volume, brightness and power keys as ACPI notifications on
 * \_SB.BIND (MSHW0040). This device has neither the "VGBI" name nor the zero
 * OEM platform revision that surfacepro3_button requires, and it has no GPIOs
 * for soc_button_array, so without this driver the events are dropped.
 *
 * See https://github.com/linux-surface/linux-surface/issues/767
 */

#include <linux/acpi.h>
#include <linux/dmi.h>
#include <linux/input.h>
#include <linux/module.h>
#include <linux/platform_device.h>
#include <linux/version.h>

#define SLSE_NOTIFY_PRESS_VOLUME_UP		0xc0
#define SLSE_NOTIFY_RELEASE_VOLUME_UP		0xc1
#define SLSE_NOTIFY_PRESS_VOLUME_DOWN		0xc2
#define SLSE_NOTIFY_RELEASE_VOLUME_DOWN		0xc3
#define SLSE_NOTIFY_PRESS_POWER			0xc6
#define SLSE_NOTIFY_RELEASE_POWER		0xc7
#define SLSE_NOTIFY_PRESS_BRIGHTNESS_UP		0xca
#define SLSE_NOTIFY_RELEASE_BRIGHTNESS_UP	0xcb
#define SLSE_NOTIFY_PRESS_BRIGHTNESS_DOWN	0xcc
#define SLSE_NOTIFY_RELEASE_BRIGHTNESS_DOWN	0xcd

static const struct dmi_system_id slse_dmi_table[] = {
	{
		.matches = {
			DMI_EXACT_MATCH(DMI_SYS_VENDOR, "Microsoft Corporation"),
			DMI_EXACT_MATCH(DMI_PRODUCT_NAME, "Surface Laptop SE"),
		},
	},
	{ }
};

/*
 * The EC only sends one press and one release per keystroke, so the hotkeys
 * rely on software autorepeat. The power key lives on a separate input device
 * without autorepeat, as logind acts on every repeat event of KEY_POWER.
 */
struct slse_buttons {
	struct input_dev *hotkeys;
	struct input_dev *power;
};

static void slse_notify(acpi_handle handle, u32 event, void *data)
{
	struct device *dev = data;
	struct slse_buttons *buttons = dev_get_drvdata(dev);
	struct input_dev *input = buttons->hotkeys;
	unsigned int key_code;
	bool pressed = !(event & 1);	/* even = press, odd = release */

	switch (event) {
	case SLSE_NOTIFY_PRESS_VOLUME_UP:
	case SLSE_NOTIFY_RELEASE_VOLUME_UP:
		key_code = KEY_VOLUMEUP;
		break;
	case SLSE_NOTIFY_PRESS_VOLUME_DOWN:
	case SLSE_NOTIFY_RELEASE_VOLUME_DOWN:
		key_code = KEY_VOLUMEDOWN;
		break;
	case SLSE_NOTIFY_PRESS_POWER:
	case SLSE_NOTIFY_RELEASE_POWER:
		key_code = KEY_POWER;
		input = buttons->power;
		break;
	case SLSE_NOTIFY_PRESS_BRIGHTNESS_UP:
	case SLSE_NOTIFY_RELEASE_BRIGHTNESS_UP:
		key_code = KEY_BRIGHTNESSUP;
		break;
	case SLSE_NOTIFY_PRESS_BRIGHTNESS_DOWN:
	case SLSE_NOTIFY_RELEASE_BRIGHTNESS_DOWN:
		key_code = KEY_BRIGHTNESSDOWN;
		break;
	default:
		dev_info_ratelimited(dev, "Unsupported event [0x%x]\n", event);
		return;
	}

	if (pressed && key_code == KEY_POWER)
		pm_wakeup_dev_event(dev, 0, true);

	input_report_key(input, key_code, pressed);
	input_sync(input);
}

static int slse_probe(struct platform_device *pdev)
{
	struct acpi_device *adev = ACPI_COMPANION(&pdev->dev);
	struct slse_buttons *buttons;
	struct input_dev *input;
	int error;

	if (!adev || !dmi_check_system(slse_dmi_table))
		return -ENODEV;

	buttons = devm_kzalloc(&pdev->dev, sizeof(*buttons), GFP_KERNEL);
	if (!buttons)
		return -ENOMEM;

	input = devm_input_allocate_device(&pdev->dev);
	if (!input)
		return -ENOMEM;

	input->name = "Surface Laptop SE Buttons";
	input->phys = "MSHW0040/buttons";
	input->id.bustype = BUS_HOST;
	__set_bit(EV_REP, input->evbit);
	input_set_capability(input, EV_KEY, KEY_VOLUMEUP);
	input_set_capability(input, EV_KEY, KEY_VOLUMEDOWN);
	input_set_capability(input, EV_KEY, KEY_BRIGHTNESSUP);
	input_set_capability(input, EV_KEY, KEY_BRIGHTNESSDOWN);

	error = input_register_device(input);
	if (error)
		return error;
	buttons->hotkeys = input;

	input = devm_input_allocate_device(&pdev->dev);
	if (!input)
		return -ENOMEM;

	input->name = "Surface Laptop SE Power Button";
	input->phys = "MSHW0040/power";
	input->id.bustype = BUS_HOST;
	input_set_capability(input, EV_KEY, KEY_POWER);

	error = input_register_device(input);
	if (error)
		return error;
	buttons->power = input;

	platform_set_drvdata(pdev, buttons);
	device_init_wakeup(&pdev->dev, true);

	error = acpi_dev_install_notify_handler(adev, ACPI_DEVICE_NOTIFY,
						slse_notify, &pdev->dev);
	if (error) {
		device_init_wakeup(&pdev->dev, false);
		return error;
	}

	dev_info(&pdev->dev, "Surface Laptop SE buttons [%s]\n",
		 acpi_device_bid(adev));
	return 0;
}

static void slse_remove(struct platform_device *pdev)
{
	acpi_dev_remove_notify_handler(ACPI_COMPANION(&pdev->dev),
				       ACPI_DEVICE_NOTIFY, slse_notify);
	device_init_wakeup(&pdev->dev, false);
}

static const struct acpi_device_id slse_acpi_ids[] = {
	{ "MSHW0040", 0 },
	{ }
};
MODULE_DEVICE_TABLE(acpi, slse_acpi_ids);

static struct platform_driver slse_driver = {
	.probe = slse_probe,
#if LINUX_VERSION_CODE < KERNEL_VERSION(6, 11, 0)
	.remove_new = slse_remove,
#else
	.remove = slse_remove,
#endif
	.driver = {
		.name = "surface_laptop_se_buttons",
		.acpi_match_table = slse_acpi_ids,
	},
};
module_platform_driver(slse_driver);

MODULE_DESCRIPTION("Surface Laptop SE hotkey driver");
MODULE_LICENSE("GPL");
